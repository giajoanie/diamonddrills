## Phase 2

### `pdf-parse` breaks under Turbopack's server bundling — fixed with `serverExternalPackages`
`pdf-parse` (built on `pdfjs-dist`) sets up a Node "fake worker" at call time by dynamically resolving a `pdf.worker.mjs` chunk; Turbopack's server-component bundling changes that file's path and the resolve fails with `Setting up fake worker failed`. Fixed by adding `pdf-parse` and `pdfjs-dist` to `serverExternalPackages` in `next.config.ts`, which tells Next.js to `require()` them natively instead of bundling. Required a dev server restart to take effect (config is only read at startup).

### Instructional area codes (BL, CM, CO, CR, EC, EI, FI, HR, IM, MK, MP, NF, OP, PD, PI, PM, PR, SE) verified via research
Extracted from real exam answer-key "SOURCE:" lines across all 6 staged Marketing exams. Two were genuinely ambiguous from context alone (NF, MK) and confirmed via web research: **NF = Information Management** (the generic/business-core version) and **MK = Marketing** (broad marketing-fundamentals area) — distinct from **IM = Marketing-Information Management** (the Marketing-cluster-specific, marketing-research-flavored version), which coexists with NF in the same exam bank. All 18 codes are stored in `src/lib/exam-import/instructional-areas.ts`. Research access was search-snippet-based (direct fetches to mbaresearch.org/deca.org were blocked in this sandbox), so confidence is "strongly corroborated" rather than verbatim-sourced — flagged if a mentor ever spots a wrong label on the review screen, it's a one-field edit, not a schema problem.

### Instructional areas stored globally, not per exam bank
The schema supports scoping `InstructionalArea` to a specific `ExamBank`, but research found these code→name mappings are stable across DECA's cluster exams (excluding the IM/NF distinction, which are two different codes, not the same code meaning different things). Seeded with `examBankId: null` (global). Note: Postgres doesn't enforce uniqueness across NULL values in the `@@unique([examBankId, slug])` index, so lookups use `findFirst` + `create` (`getOrCreateGlobalInstructionalArea`) rather than `upsert`.

### Exam PDF parser: real-world layout quirks handled, not a hypothetical
While building the parser, testing against all 6 staged real exam PDFs (2010–2014, 2026) surfaced actual defects worth recording:
- **2011 exam PDF has no extractable text layer** (scanned/image-only, 34 blank pages per `pdf-parse`). Flagged as an anomaly and skipped rather than guessed at; needs OCR or manual entry, which is out of scope for now.
- **2013 exam's first key-page header has a typo** — it still reads "...EXAM 12" instead of "...EXAM—KEY 13" like every other key page. Initially caused an off-by-one that dropped 5 real key entries and fabricated a phantom question. Fixed by detecting the body/key boundary from **content structure** (the first bare "1. `<letter>`" line — a real question stem is never that short) instead of trusting header text, which is more robust regardless of one-off template mistakes in 15-year-old PDFs.
- **Options render as either one-per-line or two-per-line** (a two-column layout used when both options are short), inconsistently across years and even within the same exam, with the column separator rendered as tabs, multiple spaces, or a single space depending on export tool. Handled with a lazy-match regex that finds the second marker (`C.`/`D.`) if present without needing a fixed separator.
- Verified parser quality directly against real data before writing any DB-persistence code: 5 of 6 files parsed 100/100 questions matched to their key with zero anomalies (see `PARSE_REPORT.md`); the 6th (2011) was correctly identified as unparseable rather than silently producing garbage.

### Mentor exam upload requires Node's `--conditions=react-server` flag for CLI scripts
`src/lib/exam-import/extract-pdf-text.ts` and `src/lib/dal/instructional-areas.ts` import `"server-only"`, which throws when required outside Next's own build (it relies on Next setting the `react-server` package-export condition to pick the no-op implementation; plain Node/`tsx` don't set that condition, so it always hits the throwing branch). Since the one-time bulk importer (`scripts/import-exam-pdfs.ts`) needs to import that same shared logic from outside Next, its npm script (`db:import-exams`) sets `NODE_OPTIONS=--conditions=react-server` rather than stripping the `"server-only"` guard from shared modules.

### "Longest streak" personal record interpreted as longest in-attempt correct-answer run
Spec §6.7 lists "personal records (best score, longest streak)" without defining what the streak counts (days practiced? correct answers in a row? attempts above some threshold?). Interpreted it as the longest run of consecutive correct answers within a single attempt (by question order) — a natural, immediately-computable test-taking record, and the one most directly motivating during practice. `computeLongestCorrectStreak` in `src/lib/exam-engine/streak.ts`, unit-tested. Flagging in case a login-streak or daily-practice-streak was intended instead — easy to add alongside this one later.

### "Score trend... per instructional area" simplified to a weighted weakest-areas list, not N line charts
Spec §6.7 asks for score trend lines "overall and per instructional area." Built the overall trend as a real line chart (`/progress`), but rendered the per-area view as `computeWeightedWeakAreas`' ranked list (already recency-weighted, matches the "weighted toward recent attempts" requirement in the same section) rather than plotting a separate line per instructional area, which would need small-multiples or an 18-line chart to stay readable. Revisit if a mentor/student specifically wants to see one area's trajectory over time — the underlying per-attempt-per-area data (`getAttemptQuestionHistory`) already supports it.

## Phase 1

### Accent color changed from teal to blue (#61a1d7)
The build spec's original design system (§3) called for teal accents; the user shared a chapter flyer with a bolder, warm-toned "vibe" and then specified `#61a1d7` (a mid blue) as the accent color to use instead. Since every component already referenced the accent via semantic Tailwind classes (`text-accent`, `bg-accent-strong`, etc.) rather than hardcoded teal hex values, this was a single-file token change in `globals.css`: `--color-accent: #61a1d7`, with `--color-accent-strong` (`#3d7ab8`) and `--color-accent-fg` (`#05121f`, dark text) chosen to keep WCAG AA contrast on solid-accent buttons (verified: ~5:1 for accent-strong, ~7.6:1 for accent, both well above the 4.5:1 AA text threshold, using dark text rather than white since white-on-this-blue was only ~2.8–4:1). Held off on the flyer's heavier poster-style typography (drop shadows, bolder display headlines) until more background assets arrive, per the user's note that more are coming — a color-token swap is safe and reversible; a full typographic treatment isn't something to guess twice.

### Product renamed: "DECA Hub" → "Diamond Drills" (full name "Mountain House Diamond Drills")
Per explicit request, replaced every "DECA Hub" reference in the app UI. There's now one designated spot for the full formal name — the browser tab's default `<title>` (`Mountain House Diamond Drills`) — and every other occurrence (page-title template suffix, meta description, footer, login heading, homepage eyebrow, Logo fallback text) uses the short name "Diamond Drills". `DECA_HUB_BUILD_PROMPT.md` (the original spec) and the historical Phase 0 entries above are left as-is since they're a record of the instructions as given at the time, not living UI copy. The chapter's actual DECA logo image (`/public/brand/deca-logo.png`) is unaffected by this — that's a separate, DECA-branded asset per spec §3, not the product name.

### Button/label casing cleanup
Fixed "Student sign up" (awkward mid-phrase lowercase) → "Sign up" on the homepage, matching the sentence-case convention already used everywhere else ("Log in", "Save new password", "Reset password"). Also flagged the ALL-CAPS "ROLEPLAY EVENT" / "WRITTEN EVENT" card labels on the dashboard as an intentional small-caps style choice (CSS `uppercase`), not a grammar issue — left those as-is.

### Mentor seed password hardcoded, per explicit user instruction (overrides the original spec)
`DECA_HUB_BUILD_PROMPT.md` §5.3 originally said the mentor seed password must come from a `SEED_MENTOR_PASSWORD` env var and never be hardcoded. The user explicitly asked to hardcode it instead — it's a shared chapter password, not a secret, and other mentors are meant to know it. `prisma/seed.ts` now sets it as a constant (`DiamondDrills2026`) directly; removed `SEED_MENTOR_PASSWORD` from `.env` / `.env.example`. Noting this here since it's a direct reversal of a security instruction in the original spec, not a silent judgment call — the user made the call.

### `/signup` was statically prerendered at build time — fixed with `force-dynamic`
`next build` marked `/signup` as static (`○`) because nothing in its render path calls a Request-time API. That baked the entire event dropdown list into the HTML/RSC payload at build time: a mentor adding, renaming, or deactivating an event afterward would not show up until the next deploy. Added `export const dynamic = "force-dynamic"` to `src/app/signup/page.tsx` so it's server-rendered per request instead (confirmed via a fresh `next build` that it now shows as `ƒ`). `/login` stays static since it has no DB-dependent content. Worth checking again in Phase 3+ as more DB-backed pages are added — same class of bug.

### `@prisma/adapter-pg`'s object-config form silently drops the username
`new PrismaPg({ connectionString: ... })` connects to Postgres but every query fails with a cryptic "no PostgreSQL user name specified in startup packet" / `DatabaseAccessDenied` error — the object form doesn't reach `pg.Pool` correctly in this adapter version. `new PrismaPg(connectionStringAsString)` works. Fixed in `src/lib/prisma.ts`; left a comment there so nobody "fixes" it back to the object form, which looks more idiomatic but is broken.

### `.env` isn't auto-loaded outside the Prisma CLI
Only `prisma.config.ts` (via its own `import "dotenv/config"`) loads `.env` for `prisma migrate`/`generate`. Running `prisma/seed.ts` directly with `tsx`, or running Vitest, does not — `DATABASE_URL` came back `undefined`, which combined with the adapter-pg bug above initially looked like a permissions problem. Added explicit `import "dotenv/config"` to both `prisma/seed.ts` and `vitest.config.ts`.

## Phase 0

### Prisma CLI version pinned to 7.10.0, not npm's "latest" tag
`npm install prisma` resolved to `8.0.0-rc.15` (npm's `latest` dist-tag currently points at a release candidate), while `@prisma/client`'s `latest` tag is the stable `7.10.0`. Installing the mismatched pair broke immediately. **Decision:** pinned `prisma` to `7.10.0` to match `@prisma/client`. Revisit once Prisma 8 has an actual stable release.

### Prisma 7's new config format
Prisma 7 removed `datasource.url` from `schema.prisma` in favor of `prisma.config.ts` + explicit driver adapters passed to `PrismaClient`. Used `@prisma/adapter-pg` with `DATABASE_URL` from the environment, and the new `generator client { provider = "prisma-client" }` (outputs to `src/generated/prisma` instead of importing directly from `@prisma/client`). This is the currently-recommended path, not a workaround.

### Password hashing library: `@node-rs/argon2` instead of the `argon2` npm package
The spec allows argon2 or bcrypt. The plain `argon2` npm package requires a native compile toolchain (node-gyp) at install time, which is fragile in constrained/sandboxed environments. `@node-rs/argon2` ships prebuilt native bindings (napi-rs) for the same algorithm and is a drop-in choice. No behavior difference for users.

### Session auth implementation: custom, not a library
Built a minimal session table (`Session` model) + httpOnly cookie holding a random token, with only the token's SHA-256 hash stored server-side — rather than pulling in NextAuth/Auth.js. The spec calls for straightforward session-based auth with hashed passwords and httpOnly cookies; a full auth framework would add surface area (OAuth providers, adapters) this app doesn't use, since the only two account types are school-issued School ID + password.

### DECA logo asset not yet provided
`/public/brand/deca-logo.png` doesn't exist yet (the spec describes it as "chapter-provided"). Built `Logo` as a small client component that renders the image and falls back to a text "Diamond Drills" wordmark on load error, so the app doesn't break and nothing resembling an official DECA logo is fabricated. **Action needed from you:** drop the real file at that path (and it'll pick it up automatically, including as favicon) — see `next.config`/`layout.tsx` icon metadata.

### Event categorization: Professional Selling stays WRITTEN
The spec explicitly says: *"Keep it selectable as WRITTEN unless I say otherwise."* Research turned up that DECA's own taxonomy treats Professional Selling, Financial Consulting, and Hospitality and Tourism Professional Selling as one category ("Professional Selling and Consulting") that behaves more like a roleplay (live judged presentation + exam) than a written deliverable. Followed your explicit instruction anyway: Professional Selling = `WRITTEN`; the other two stay `ROLEPLAY` as originally hand-typed. This leaves a real inconsistency across the three sibling events — flagged in `EVENT_VERIFICATION.md` §3 item 5 in case you'd rather make them consistent.

### Exam bank enum corrections applied without asking
Two corrections from research were applied directly rather than flagged as an open question, because they're unambiguous and structural, not judgment calls:
- All five "Principles of X" events use the **Business Administration Core** exam bank, not their own cluster's exam (this matches the spec's own stated default assumption in §4.1 — research just confirmed it).
- "Business Law" and "Sports and Entertainment Marketing" are not standalone DECA exam banks; Business Law and Ethics TDM and all three SEM events route to Business Management and Administration and Marketing respectively.

### Financial Literacy Project's cluster placement — left as hand-typed, flagged uncertain
Research couldn't confirm with confidence whether DECA files this under Business Management and Administration (as hand-typed) or Personal Financial Literacy. Seeded under BMA for now since that's the existing hand-typed placement; see `EVENT_VERIFICATION.md` §4 for the open question.

### Event research was search-snippet-based, not a direct document read
The sandboxed environment blocked direct `WebFetch` access to deca.org, decaplus.org, and every state-DECA site tried, so `EVENT_VERIFICATION.md` is built entirely from web-search snippets rather than a first-hand read of DECA's current Guide/Exam Blueprint PDFs. Confidence per-claim is noted in that file. **Recommend a human spot-check the Exam Blueprints PDF and the current-year Guide PDF before treating minute counts, page limits, or the Financial Literacy Project placement as final** — none of those numbers are hard-coded into the schema yet, so nothing breaks if they change.

### Exam PDFs will arrive incrementally
You uploaded one exam (`2026 Marketing ICDC Exam`) mid-Phase-0; it's stored at `seed/exams/marketing/2026_marketing_icdc_exam.pdf` for the Phase 2 PDF-import pipeline to pick up. More will presumably follow before Phase 2 begins — no action needed now, just noting where uploads land.

### This Next.js version (16.3.5) is ahead of training data — checked bundled docs before writing more code
`AGENTS.md`/`CLAUDE.md` (auto-generated by `next dev`) correctly flagged that this Next.js version may have breaking changes vs. training data, and pointed at real bundled docs in `node_modules/next/dist/docs/`. Confirmed this is genuine (the generator script and docs directory both exist) and read the version 16 upgrade guide plus the authentication guide before proceeding. Two things affect this codebase directly:

1. **`middleware.ts` is renamed to `proxy.ts`** (exported function `proxy`, not `middleware`); the `edge` runtime is no longer supported for it (runs on `nodejs` only, which suits us anyway since our session lookup needs Prisma/node-postgres). No `proxy.ts` exists yet — note this for whoever adds one in Phase 1, and per Next's own guidance, use it only for optimistic redirects, not as the real auth check.
2. **Layouts are not a reliable place for auth checks.** Next 16's partial rendering means a shared `layout.tsx` does not re-run on client-side navigation between sibling routes, so a check placed only in a layout won't re-verify the session on every route change, and a layout doesn't stop the rest of the route tree from rendering/streaming regardless. The documented pattern is a `cache()`-memoized `getSessionUser()`/`requireUser()` (already updated in `src/lib/auth/session.ts` and `src/lib/auth/guards.ts` to use React's `cache()`) called from **every** protected `page.tsx`, Server Action, and Route Handler — not just from the layout. **Applies directly to Phase 1's "role-based route protection" requirement — student/mentor route protection must be enforced per-page, with layouts only used for shared chrome.**

Also confirmed already-correct: `cookies()` usage (async, `await cookies()`) matches the current API; ESLint flat config matches what's already generated; ID param helper types (`LayoutProps<"/">`) match the new `next typegen` convention already in the scaffolded `layout.tsx`.

### Local dev database: native Postgres, not Docker
`docker-compose.yml` is included per the spec's tech stack (and is what you should use on a normal machine), but this sandbox's Docker daemon isn't available to me. Used the sandbox's pre-installed native PostgreSQL 16 instead, with a `deca_hub` role/database matching the same credentials `docker-compose.yml` would produce, so `DATABASE_URL` in `.env` works either way. This only affects how *I* verified the schema in this session — it doesn't change anything about how you'd run this locally.

### Assignment types simplified for Phase 3 scope
`EXAM`-type assignments store their config (`examBankId`, `questionCount`, `timeLimitMinutes`) as a randomized draw, reusing the existing practice-exam engine from Phase 2 rather than building a separate fixed-question-set authoring flow — a mentor picks a bank and a count, and each student gets a fresh random draw when they take it (task #33). `PRACTICE_ROLEPLAY`-type assignments are, for now, functionally identical to `FILE_SUBMISSION` (student uploads written prep notes/materials) since the live roleplay simulator is a Tier 2 feature (Phase 5) that doesn't exist yet — the type is still tracked distinctly on the model so the simulator can hook into it later without a schema change.

### Assignment targeting: one target mode per assignment, multiple values within it
`AssignmentTarget` supports mixing target types on one assignment (e.g., grade 11 AND a specific event) per its schema comment, but the creation form only lets a mentor pick one mode (Everyone / Grade / Event / Cluster / Individual student) and multi-select within it — creating one `AssignmentTarget` row per selected value. This covers the realistic cases (assign to a grade, a roster, specific students) without the UI complexity of combining modes; nothing stops a future form from allowing combined targeting since the DAL/visibility logic (`src/lib/assignments/visibility.ts`) already treats the target list as "visible if ANY row matches," mirroring the resource-visibility pattern from Phase 3 resources.

### PRACTICE_SESSION_START/COMPLETE activity types are reserved for the Tier 2 roleplay simulator, not exam practice mode
The schema's `ActivityType` enum has both `EXAM_START`/`EXAM_COMPLETE` and `PRACTICE_SESSION_START`/`PRACTICE_SESSION_COMPLETE`. Confirmed by checking what each pairs with: `EXAM_START` already fires for every exam attempt regardless of mode (including practice-by-area and missed-question review, with `mode` in its metadata), while `PRACTICE_SESSION_*` has no existing caller and its natural home is `RoleplayPracticeSession` (Tier 2, Phase 5, not built yet). So Phase 4's "practice sessions per student per week" KPI is computed by filtering `EXAM_START` logs to practice-type modes, not from a separate activity type — nothing new needed here for Phase 4.

### ASSIGNMENT_VIEWED/FEEDBACK_VIEWED logged client-side on mount, so dev-mode double-fires
Both are logged from a tiny client component (`ViewLogger`) that calls a Server Action in a `useEffect` on the assignment detail page, mirroring the existing `logResourceOpen` pattern. In development, React's Strict Mode double-invokes effects, so you'll see two identical log rows per page view in `next dev` — this does not happen in production (`next build && next start`) and isn't worth guarding against with dedup logic for an engagement-timeline log.

### Mentor dashboard date-range filter scopes "due within range," and assignment completion has an explicit empty state
The dashboard's date-range filter applies to exam attempts (`submittedAt`), rubric scores (`scoredAt`), resource opens (`createdAt`), and assignment due dates (`dueAt`) — all "did this happen in this window" fields, not "was this assignment created in this window." With no dates picked, it defaults to all-time-through-now, which means an assignment due in the future is correctly excluded from the completion-rate denominator (it isn't over yet, so a 0% wouldn't mean anything). That surfaced a real bug during verification: with every test assignment due in the future, the sample size was zero but the UI still printed "0% completed," which reads as a chapter-wide failure rather than "no data." Fixed by returning a `sampleSize` alongside the rate and showing "No assignments due in this period yet" when it's zero — same empty-state pattern already used for the score-vs-baseline card.

### Assignment completion/on-time rate is resolved against each assignment's real target audience, not just existing Submission rows
Since Submission rows are only created lazily when a student first submits (Phase 3 decision — no pre-created NOT_STARTED rows), computing a true completion rate requires knowing who an assignment *should* reach. The mentor dashboard reuses `isAssignmentVisibleToStudent` (the same pure function the student-facing assignment list uses) against each filtered student's visibility context to build the eligible-student set per assignment, then checks that set against actual Submission/ExamAttempt rows. This means the KPI is only as complete as the cohort passed in (grade/cluster/event filters narrow both the eligible set and the "did they do it" check consistently), which is the intended behavior for a filtered chapter view.

### Competition-level filter deferred from the mentor summary dashboard
Spec §9.2 lists "grade, cluster, event, competition level, date range" as filters on every mentor view, but competition level isn't an attribute of a student or enrollment — it only exists on `Resource.competitionLevel` and `CompetitionResult.level`. Applying it to the chapter-wide summary dashboard (active students, score-vs-baseline, weak areas, etc.) has no natural meaning, so it's left off that page. It belongs on views where it's meaningful — CSV exports (task #45) and the competition-results entry screen (task #44) — where it's implemented directly against those models.

### Roleplay simulator: self-rating rubric chosen at completion, not at session start
`RoleplayPracticeSession` has no `rubricId` column, only a JSON `selfRatings` field. Rather than add a migration, the rubric picker appears after the presentation timer ends, right before the student rates themselves — `selfRatings` is keyed by criterion ID, which is globally unique across rubrics, so no session-level rubric reference is actually needed to interpret the stored ratings later (the results page cross-references criterion IDs against all rubrics, active or not, to render names/max points). This also means a student can rate themselves against any rubric a mentor has built, not just one tied to their event — reasonable for self-assessment, less so if this ever needs to gate a mentor-facing view of "the roleplay rubric for event X" (Judge Mode, Tier 3, will need a firmer link and may need to add that column then).

### Roleplay timers are two sequential phases derived from one `startedAt`, no separate phase-transition field
Prep spans `[startedAt, startedAt + prepSeconds)` and presentation spans `[startedAt + prepSeconds, startedAt + prepSeconds + presentationSeconds)`, both computed client-side each tick from the single server-set `startedAt` timestamp — mirroring the exam engine's server-authoritative timer pattern (`computeRemainingSeconds`) rather than introducing new state. A student who closes the tab and comes back mid-prep or mid-presentation resumes at the correct phase and remaining time automatically; there's no separate "pause" concept, matching how competition prep/presentation time isn't pausable either.

### Case study resource picker isn't scoped to the specific roleplay event
`startRoleplaySession`'s case-study dropdown reuses `getVisibleResourcesForStudent(userId, { type: "CASE_STUDY" })`, which scopes to the student's current cluster/event visibility broadly (per Phase 3's resource-visibility rules) rather than narrowing to only the one roleplay event being practiced. A student with both a roleplay and written event could see a case study tagged to either. Acceptable for now since case studies are mentor-curated and typically tagged narrowly already; a tighter per-event filter would need a resource DAL variant that also returns `resourceEvents`/`resourceClusters`, which the current visibility query doesn't select.

### Team linking is mentor-driven, not a student join/invite flow
Spec §11 says "link teammates for TDM and team written events," without specifying who initiates the link. Rather than build student-facing invite/accept requests, mentors create teams directly from a roster picker (`/mentor/teams`), consistent with how every other administrative flow in this app (accounts, resets, event changes) is mentor-driven. A student can only be on one active team per event (enforced in `createTeam`); "removing" a member or disbanding a team soft-deletes via `TeamMember.leftAt` rather than a hard delete, preserving history for a future "past teams" view.

### "Share team assignments and results" scoped to competition results and a dashboard teammate display, not shared Submission rows
`CompetitionResult.teamId` already existed in the schema for exactly this — recording a team result now creates one row per active member sharing the same teamId/scores/placement via `recordCompetitionResult`'s team mode. For assignments, `Submission` is still one row per (assignmentId, userId) with no teamId (a Phase 3 decision to avoid pre-created rows), so full assignment-sharing would need a schema change to either add a teamId to Submission or introduce a "shared submission" concept; that's deferred. What's built now: teammates show on each other's dashboard event card (`getTeamForStudentEvent`), so students on a team at least know who they're paired with — actual submission sharing on a specific assignment is left for a future pass once there's a concrete team-assignment workflow to validate it against.

### Missed-question spaced repetition: Leitner-style 1/3/7-day intervals, wired into logic the schema already anticipated
`MissedQuestion.correctStreak`/`isMastered`/`nextDueAt` were already in the Phase 0 schema and `correctStreak`/`isMastered` were already being maintained by `finalizeAttempt` since Phase 2 — but `nextDueAt` was never touched after its `now()` default, so "missed question review" mode pulled every non-mastered miss in one flat batch regardless of when it was last seen, which isn't spaced repetition, just a retry queue. Added `computeNextDueAt(correctStreak, now)` (1 day at streak 0, 3 days at streak 1, 7 days at streak 2, mastered at streak 3 — unchanged mastery threshold, now exported as `MASTERY_STREAK` instead of a magic number) and wired it into both branches of `finalizeAttempt`'s per-question update, plus filtered the `MISSED_REVIEW` start-exam query and the dashboard/start-page counts down to `nextDueAt <= now`. Verified end-to-end: a fresh miss schedules exactly 1 day out and is correctly hidden from "due now" until then. The exact interval values (1/3/7 days) are a reasonable default, not something the spec pins down — a mentor-configurable version would be a natural follow-up if chapters want to tune it.

### Personalized recommendations: a new dashboard card, reusing two features that already existed
Spec §11's "personalized recommendations for students" turned out to be mostly already built — `getRecommendedResources` (Phase 2) already personalizes `/resources`, and `/exam/start` already accepts `?mode=PRACTICE_AREA&area=<id>` for a targeted practice exam. The one missing piece was surfacing a recommendation *on the dashboard itself* rather than requiring a student to go find it. Added a "Recommended for you" card computed from the same `computeWeightedWeakAreas` used elsewhere (recency-weighted accuracy across a student's own attempts, top 3), each with a `Practice this →` link straight into the existing deep-link. No new scoring logic, no new page — just a new entry point into two features that already worked. Correctly renders nothing for a student with zero completed attempts (nothing to compute a weak area from), which was confirmed during verification to be the intended empty state, not a bug.

### Lesson-plan reason text now names a trend, not just a flat percentage
`generateLessonPlanRecommendations` (Phase 4, task #43) only ever said "X is the weakest area, averaging Y% accuracy" — true but static, even for an area that's already recovering or getting worse. Added `computeAreaTrend` (`src/lib/analytics/trend.ts`): splits a student-or-chapter's chronologically-ordered correct/incorrect results in half and compares earlier-half vs. later-half accuracy, classifying `improving`/`declining`/`stable` at a >5-point-change threshold (under 4 data points, or an empty set, is always `stable` — too little signal to call a direction). `trendByArea` is computed once per instructional area in `getLessonPlanRecommendations` (`src/lib/dal/analytics.ts`) by re-sorting the same `questionResults` rows already being fetched (added `submittedAt` to the existing `examAttempt` select — no new query), then threaded through into the reason string via a `TREND_CLAUSES` map so the sentence reads "...averaging 40% accuracy, and has been trending down recently — worth prioritizing" instead of a bare period. Threshold picked to avoid over-calling noise on small sample sizes as a reasonable default, same spirit as the mastery-streak and spaced-repetition intervals above — not something the spec pins a number to.

### Judge Mode: the link itself is the credential, no separate token column
`JudgeScore.judgeId`/`judgeName` already existed in the Phase 0 schema for exactly this — a mentor or peer judge scores a live practice roleplay from their phone, possibly without an account. Rather than add a signed-token column to `RoleplayPracticeSession`, the judging link is simply `/judge/<sessionId>` — the session's own `cuid()` id is already a 25-character random identifier, unguessable in practice, so it doubles as the share secret the same way a lot of "anyone with the link" sharing schemes work. The route (`src/app/judge/[sessionId]/page.tsx`) is deliberately public — no `requireRole` — and shows only what a judge needs (student's first name, event name, active rubrics), never the student's private prep notes or self-ratings, which stay behind the authenticated `/roleplay/[sessionId]` routes. A visitor who happens to already be logged in (checked via the existing optional `getSessionUser()`, no redirect) is recorded via `judgeId` and skips the name field; everyone else types a display name into `judgeName`. Submitting is possible any time a session exists, not gated on the student having clicked "complete," since live judging happens during the presentation itself, before the student's own self-rating step. Judge feedback then surfaces on the student's `/roleplay/[sessionId]/results` page alongside their self-rating. This also exposed that Phase 5's roleplay simulator never actually logged `ROLEPLAY_SESSION_START`/`COMPLETE` to `ActivityLog` despite both being defined in the Phase 0 schema — added those two calls now, needed for the upcoming activity timeline (task #58) to have real data to show.

### Competition Simulation Mode: event-first entry point, no new schema or session-linking column
`ExamMode.COMPETITION_SIMULATION` already existed in the Phase 0 schema but was never wired up. "Timed exam followed immediately by a timed roleplay, like competition day" only makes sense for a ROLEPLAY-category event that also has an exam component (`Event.hasExam` — a DECA "Series" event, which has both a 100-question exam and a roleplay). The existing `/exam/start` flow is bank-first (pick a bank, then a mode), which doesn't carry an eventId through to the roleplay leg, so this got its own small event-first entry point instead: `/exam/simulation/start` lists the student's current events that are both ROLEPLAY and `hasExam`, and `startCompetitionSimulation` (`src/lib/actions/exam-engine.ts`) always uses the full 100Q/90-minute preset (real competition format) and threads the eventId onto the created `ExamAttempt` (added an `eventId` parameter to the existing `startAttemptWithQuestionIds`, which the schema already supported but no caller had used). The chain itself needs no new model or linking column: the exam results page checks `attempt.mode === "COMPETITION_SIMULATION"` and, if so, shows a "start your roleplay now" button that posts straight to a one-line wrapper (`startRoleplayFromExamResults`) around the existing `startRoleplaySession` action with that same eventId — reusing the whole roleplay simulator (and, transitively, Judge Mode) exactly as built, rather than inventing a separate "simulation session" concept.

### Student activity timeline reuses (and completes) the mentor's engagement-timeline labels
Building `/activity` — a student-facing chronological feed of their own `ActivityLog` rows — surfaced that the mentor's per-student "Engagement timeline" (Phase 4, task #42) had a local `ACTIVITY_LABELS` map that was already stale: it predated `INTERVENTION_LOGGED`, `ROLEPLAY_SESSION_START/COMPLETE`, `PRACTICE_SESSION_START/COMPLETE`, and `JUDGE_SCORE_SUBMITTED`, so any student with those newer activity types would show raw enum strings on the mentor's view. Extracted it into `src/lib/analytics/activity-labels.ts` as `ACTIVITY_LABELS: Record<ActivityType, string>` — typed against the enum itself so TypeScript now refuses to compile if a future `ActivityType` is added without a label — and pointed both the mentor's timeline and the new student one at the same `describeActivity()` function. Also caught one more activity type defined in the Phase 0 schema but never actually logged: `INTERVENTION_LOGGED` (added to `logIntervention` in `src/lib/actions/mentor.ts`) — the roleplay ones were fixed already, in the Judge Mode entry above.

### Personal records and streaks: a distinct "practice consistency" streak, not a duplicate of the exam engine's
The Progress page already had a "Personal best" score and a "Longest correct streak" (`computeLongestCorrectStreak`, Phase 2) — but that streak measures consecutive correct *answers within one exam attempt*, not practice habit consistency, which is the more common reading of "streaks" for this spec bullet. Added `computePracticeStreak` (`src/lib/analytics/streaks.ts`): given a set of activity timestamps, dedupes to calendar days and returns both the current consecutive-day streak (still alive if the most recent activity was today or yesterday — a streak isn't broken until a full day passes with none) and the longest ever. "Practice" is deliberately narrower than every `ActivityLog` type — `getPracticeActivityDates` (`src/lib/dal/analytics.ts`) filters to `EXAM_START`, `PRACTICE_SESSION_START`, `ROLEPLAY_SESSION_START`, and `SUBMISSION_CREATED`, excluding `LOGIN`/`LOGOUT` noise so opening the app without doing anything doesn't count. Surfaced as two more stat cards on the existing Progress page (and a smaller one in its no-completed-exams empty state, so a student who's only done roleplay practice still sees something).

### Advanced mastery prediction finally populates the Phase 0 MasteryEstimate table
`MasteryEstimate` (userId, examBankId, instructionalAreaId, estimatedMastery 0-1) existed in the schema since Phase 0 but was never written to — the weak-area displays built so far (`computeAreaBreakdown`, `computeWeightedWeakAreas`) all compute a flat or linearly-recency-weighted accuracy on the fly instead. Built `predictMastery` (`src/lib/analytics/mastery.ts`) as a genuinely more advanced model: per-*question* exponential recency decay (half-life 10 questions) rather than per-*attempt* linear weighting, plus Bayesian shrinkage toward a neutral 50% prior weighted by 5 pseudo-observations, so a student who's answered only 2-3 questions in an area doesn't get reported as "0%" or "100%" mastery — the estimate stays cautious until there's enough signal. `finalizeAttempt` (`src/lib/actions/exam-engine.ts`) now recomputes and upserts `MasteryEstimate` for every instructional area touched by a just-completed attempt, using that student's *entire* chronological history in the bank (not just the current attempt), and both the student's Progress page and the mentor's per-student profile page render a new "Predicted mastery by instructional area" list from the cached table. Confidence tier (low/medium/high by sample size) is part of the pure function's return value but isn't persisted — the schema only has room for the estimate itself — so it's currently an internal signal on the write path rather than shown in the UI; adding a `sampleSize` column would be a natural follow-up if that turns out to matter to mentors.

### Resource search: keyword match on name/description, scoped to the student-facing library only
Added a `q` text field to `/resources`'s existing filter form, matching case-insensitively against a resource's `name` or `description`. Mirrors the project's usual split: a pure `matchesSearchQuery` (`src/lib/resources/search.ts`, tested) documents the exact matching rule, and `getVisibleResourcesForStudent` (`src/lib/dal/resources.ts`) applies the equivalent Prisma `contains`/`mode: "insensitive"` filter, ANDed with the existing grade/event visibility and type/area/level filters. Scoped to the student-facing library (`/resources`) only, not the mentor's own resource-management page (`/mentor/resources`) — that page is a small, self-curated upload list a mentor already knows the contents of, whereas the student library is the one that actually needs to be searchable as it grows across every visible cluster/event.

### Automatic study-plan generation: one shared chapter-wide competition date, round-robin over weak areas
Populates `StudyPlanItem` (userId, instructionalAreaId, resourceId, dueDate, completed) — anticipated by the Phase 0 schema but unused until now. "The competition date" comes from the soonest upcoming `CalendarEvent` that has a `level` set (District/State/ICDC) — there's no per-student or per-event competition-date field in the schema, so this is chapter-wide: every student studying toward the same next competition, consistent with how the competition calendar (Phase 5, task #50) already works. `generateStudyPlan` (`src/lib/analytics/study-plan.ts`, tested) is a pure function that takes the student's weakest-area ids (from the same `computeWeightedWeakAreas` used elsewhere), spreads sessions evenly between now and the competition date (minimum 2-day spacing, capped at 15 sessions so a competition a year out doesn't generate an absurdly long list), and cycles round-robin through the weak areas so the single weakest one doesn't crowd out the others. Each session is tagged with one visible resource for that area when one exists (`getResourceForArea`, `src/lib/dal/resources.ts`). Regenerating (`/study-plan`, "Regenerate plan") deletes only *incomplete* items and recreates from scratch — completed ones are left alone as a record of what was actually done, rather than being wiped every time the plan is rebuilt.

### PM CDE Impact Dashboard: engagement-vs-improvement as the causal story a CDE report needs
The mentor dashboard (Phase 4) already showed chapter-wide score-vs-baseline averages, but a Project Management CDE written report needs more than one number — it needs to argue that *using the platform* correlates with *improvement and outcomes*. Added `getPmCdeImpactData` (`src/lib/dal/analytics.ts`), which reuses `getMentorDashboardData`'s cohort resolution and before/after averages wholesale (no duplicated logic) and layers on two new breakdowns via `computeEngagementVsImprovement`/`computeOutcomesByEngagement` (`src/lib/analytics/pm-cde.ts`, tested): students bucketed into low/medium/high engagement by how many practice-type `ActivityLog` entries they have in the filtered date range (reusing the same `PRACTICE_ACTIVITY_TYPES` list already established for the practice-streak feature), cross-referenced against their score change vs. baseline and their competition advancement rate (`CompetitionResult.advanced`, OR-reduced across a student's results — "did they ever advance" rather than "did their most recent result advance"). Rendered at `/mentor/pm-cde-impact` as plain tables rather than new chart components — deliberately report-friendly (copy/paste-able into a written document) rather than another interactive dashboard widget, consistent with "formatted for use in the written report" being the actual spec ask.

## Phase 7

### Security review (task #65): findings, fixes, and deliberate non-fixes
A dedicated audit of auth checks, file access, rate limiting, secrets, and injection risks turned up several real issues, now fixed:

- **Critical/high — two unguarded Server Actions.** `startAttemptWithQuestionIds` and `finalizeAttempt` (`src/lib/actions/exam-engine.ts`) were exported from a `"use server"` file with no internal auth check — since *every* export of such a file becomes its own directly network-callable endpoint regardless of who else imports it, either function could be invoked directly by an unauthenticated client with an arbitrary `userId`/`attemptId`, letting someone fabricate exam attempts for other students or force-submit another student's in-progress exam. Fixed by moving both (plus their private `updateMasteryEstimates` helper) into `src/lib/exam-engine/attempt-lifecycle.ts` — a plain module with no `"use server"` directive — so they're only reachable as regular function calls from already-authenticated, ownership-checked callers (`startExam`, `startCompetitionSimulation`, `submissions.ts`, and `submitExam`/`abandonExam`/the exam page), never as a standalone endpoint. General lesson for anything added later in an actions file: a helper meant to be "internal to this file" isn't, if the file has the directive — it needs its own auth check or its own non-`"use server"` home.
- **High — file-serving path traversal.** `src/app/files/[...path]/route.ts` authorized only `segments[0]`/`segments[1]` but read the *full* joined path, so an extra `..` segment after a resource id the user legitimately owns could resolve to a completely different file (e.g. another student's submission). Fixed by requiring exactly 3 clean segments (matching the only shape `saveUploadedFile` ever produces) with no `.`/`..`/slash characters, checked before the auth branch even runs. Also hardened `readStoredFile`'s containment check (`src/lib/files/storage.ts`) from a bare `startsWith(STORAGE_ROOT)` — which a sibling directory like `uploads-backup` can falsely satisfy — to a proper `path.relative` check.
- **Medium — login lockout reset on every cycle.** `nextFailedLoginState` (`src/lib/auth/lockout.ts`) reset the failed-attempt counter to 0 at the moment of locking, so an attacker got a fresh 5 guesses every 15 minutes forever. Now the counter is never reset by a lockout (only a successful login resets it) and each lockout past the threshold doubles the wait, capped at 24h.
- **Medium — hardcoded shared mentor seed password.** `prisma/seed.ts` had a single password string committed to git for every seeded mentor account, readable by anyone with repo access even before that mentor's first (forced-change) login. Now generates a random temporary password per mentor at seed time via the existing `generateTemporaryPassword()` and prints it once to the console — never persisted anywhere but the hash.
- **Medium — unvalidated judge scores.** `submitJudgeScore` (`src/lib/actions/judge.ts`) trusted whatever `criterionId`/score pairs the client posted, so a score could exceed its criterion's `maxPoints` or reference a criterion from an unrelated rubric. Now looks up the real criteria and clamps each score to `[0, maxPoints]`, drops unknown criterion ids, and caps `judgeName`/`comments` length.
- **Medium — no rate limiting on signup or Judge Mode submission.** Both were fully open to scripted abuse (mass account creation; flooding one roleplay session with fake judge scores). Added a small in-memory sliding-window limiter (`src/lib/rate-limit.ts` — intentionally not Redis-backed; this targets a single small-school deployment, and the doc comment flags the multi-instance limitation) applied to `signup` (5/hour per IP, via `x-forwarded-for`) and `submitJudgeScore` (20/10min per session).
- **Medium — no upload size limit.** Added a shared `MAX_UPLOAD_BYTES` (25MB) cap in `src/lib/files/storage.ts`, checked in both `createResource` and `submitAssignmentFile` before the file ever touches disk.
- **Low — CSV/formula injection.** A judge name, competition note, or similar free-text field starting with `=`/`+`/`-`/`@` would be interpreted as a formula by Excel/Sheets on open. `escapeCsvField` (`src/lib/csv/export.ts`) now prefixes such *string* fields (never numeric ones, so a legitimately negative score isn't corrupted) with a leading apostrophe.
- **Low — missing security headers.** Added `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, and HSTS via `next.config.ts`'s `headers()`. Deliberately did **not** add a Content-Security-Policy — getting one wrong (blocking recharts, Google Fonts, or an inline style) is worse than having none, and it needs a careful pass of everything the app actually loads, which wasn't in scope for this review.
- **Informational, left as-is.** The signup form's "That School ID is already registered" message technically enumerates valid school IDs — a common, generally-accepted tradeoff for signup UX, and schoolIds aren't secret (a mentor's roster already has them all), so no change made. Removed the unused `SESSION_SECRET` env var (`.env.example`) — sessions use random tokens hashed with SHA-256, not HMAC, so it was never read anywhere. Confirmed no `dangerouslySetInnerHTML`/`eval` anywhere in the codebase, and `.env` is properly gitignored (only `.env.example` is tracked).
